# Voice Bot — голосовой бот для звонков по скрипту

Серверный голосовой бот на **LiveKit Agents** (Python). Воркер ведёт разговор по
сценарию; для локальных боевых звонков в docker поднимается и веб-клиент.

Стек одной строкой: **LiveKit** (транспорт звука) + **OpenAI** / локальный
STT / **LangGraph** (распознавание и «мозг») + **ElevenLabs** (голос).
Логика диалога при провайдере `openai` — в сценарном промпте; при `agent` — во
внешнем графе.

---

## Как это устроено

```
Браузер ──звук──▶ LiveKit ──▶ Агент (воркер) ──▶ голос обратно клиенту
                              ├─ STT   речь → текст      (OpenAI или свой сервис)
                              ├─ LLM   формулирует ответ (OpenAI или LangGraph)
                              ├─ TTS   текст → голос      (ElevenLabs)
                              ├─ VAD   ловит конец реплики (Silero)
                              └─ фон   офис + клавиатура (BackgroundAudioPlayer)
```

- **LiveKit-сервер** — «труба», возит звук. Поднимается в docker.
- **Агент** — этот проект. Отдельный процесс-воркер, подключается к серверу.
- **Playground** — официальный [`agent-starter-react`](https://github.com/livekit-examples/agent-starter-react),
  собирается из git в контейнере; сам выдаёт JWT через `/api/token`.
- STT / LLM / TTS / VAD — готовые плагины (`session.py`); LLM и STT сменные.
- Свой код — сценарий, системный промпт (путь `openai`), настройки фона и прокси.

## Сменный LLM

«Мозг» переключается одной переменной — как STT:

```bash
# по умолчанию — OpenAI (ничего менять не нужно)
VOICE_BOT_LLM_PROVIDER=openai

# удалённый граф на LangGraph Server (отдельный стек)
VOICE_BOT_LLM_PROVIDER=agent
VOICE_BOT_AGENT_URL=http://172.17.0.1:8127
VOICE_BOT_AGENT_GRAPH=vector_agent
```

При `agent` инструкции бота пустые: промпт собирает сам граф. Сценарий бота в
этом режиме не участвует — из него берётся только идентификатор в строку лога.

## Два канала к мозгу

При `llm_provider=agent` бот держит с мозгом две независимые связи.

```
клиент говорит ──▶ vector_checker   лайв-канал, свой тред
                   (закрывает шаги, греет контекст)

клиент договорил ─▶ vector_agent    основной ход, свой тред
                   (берёт открытые шаги и говорит)
```

**Треды разные, скрипт один.** Тред LangGraph сериализует запуски: пока тред был
общий, служебная отправка вытесняла основной ход и звонок рвался с
`UserInterrupt`. Теперь лайв-канал уходит на свой UUID-тред, а в `configurable`
передаётся `call_id` — идентификатор звонка, равный треду основного хода. Мозг
ключует скрипт этим идентификатором, поэтому оба канала работают с одним
скриптом.

`multitask_strategy="interrupt"` у служебной отправки сохранён: теперь она бьёт
только по своим проходам — свежий кусок речи вытесняет устаревшую гипотезу.

**Что уходит в лайв-канал.** Накопленный текст реплики плюс два поля:
`partial_utterance_id` — идентификатор реплики, меняется при сбросе буфера, и
`partial_is_final` — признак финального распознавания. Без идентификатора мозг
пропускал разбор, когда реплика оказывалась той же длины, что предыдущая.

## Приветствие

При `llm_provider=agent` вступительную фразу произносит **мозг**: граф зовётся
сразу на пустой истории, и приветствие приходит обычным первым шагом скрипта.
Так текст живёт в одном месте — вместе с требованиями, образцами и правилами речи.

Цена решения: первая фраза появляется не мгновенно, её генерирует модель — это
примерно полторы-две секунды после подключения. Осознанный размен на
единственную точку правды.

При `llm_provider=openai` всё как было: дословная `opening_line` из сценария
через `session.say`.

## Структура

```
src/voice_bot/
├── config.py            # настройки из окружения (Pydantic Settings)
├── logging_setup.py     # единый формат логов
├── agent/
│   ├── main.py          # точка входа воркера (dev / console / start)
│   ├── session.py       # сборка сессии из плагинов + лайв-канал
│   ├── script_agent.py  # агент со сценарным промптом (путь openai)
│   └── token.py         # JWT для ручной вставки в клиент (make token)
├── scenario/            # сценарий для пути openai
└── stt/                 # клиент своего сервиса распознавания
```

Провайдера STT, TTS и VAD меняем **только** в `agent/session.py` — остальной код
о конкретном провайдере не знает.

## Что нужно для запуска

```bash
uv sync
uv run python -m voice_bot.agent.main console   # микрофон, без LiveKit
uv run python -m voice_bot.agent.main dev       # воркер против сервера
docker compose up --build                        # сервер + бот + веб-клиент
uv run ruff check src tests && uv run pytest -q
```

## Диагностика звонка

```bash
docker compose logs agent --no-log-prefix | grep -E "\[(live|STT)\]|Бот"
```

| Строка | Что показывает |
|---|---|
| `[STT] Клиент` | распознанная реплика, длительность, время распознавания |
| `[live] отправка` | текст, лайв-тред, `call_id`, идентификатор реплики, признак финала |
| `Бот (e2e=…)` | реплика и время от конца речи клиента до готовности ответа |

Здоровый звонок: `UserInterrupt` в логах мозга отсутствует, `e2e` держится в
пределах трёх секунд, каждая реплика уходит в лайв-канал со своим
идентификатором.

## Совместимость

Ветка лайв-канала и ветка мозга выкатываются **вместе**. Бот с новым лайв-тредом
против старого мозга положит скрипт на два разных ключа, и каналы разъедутся:
чекер перестанет видеть шаги, которые уже прозвучали.

---

## Куда расти

* **Потоковое распознавание.** Сейчас плагин STT объявлен как `streaming=False`,
  промежуточных результатов нет — сервис распознаёт реплику целиком. Из-за этого
  лайв-канал получает ровно одну отправку на реплику и греться во время речи
  ему нечем. Появятся промежуточные результаты — прогрев заработает по-настоящему.
* **Мгновенное вступление.** Когда появится потоковая отдача речи, первую фразу
  можно будет вернуть к мгновенной, не заводя вторую копию текста.
